# Spotlight Rule

完整操作规格在 `00_Resources/spotlight-rule.md`。这篇讲 *为什么* — 规则背后的设计选择，和它解决什么问题。

## 它解决的问题

LLM assistant 默认浮出一堆「你可能觉得有意思」。造成 3 个问题：

1. **量上的疲劳。** 一周内用户开始忽略所有浮出项。
2. **谄媚。** Agent 浮出用户已经同意的东西，因为那些更容易打成「高价值」。
3. **信号陈旧。** 没有校准 loop，阈值会漂到 agent 的先验值 — 通常偏低。

Spotlight Rule 修这 3 个问题。

## 机制

### 量化的门槛
3 因子加权分 ≥ 7.0，置信度 ≥ medium。否则默认 = 沉默。

### 第一性原理强制
Surprise 维度（权重 0.3）打分 *针对用户已有模型*。具体：
- 10 = 打破假设
- 5 = 确认既有模型
- 1 = 重述已知

**只确认用户先验的 spotlight 凑不到 7.0**，因为 Surprise 拉低分。这是防谄媚机制。

### 量的上限
每 session 最多 3 个 spotlight。第 4 个候选必须比已发的最低分高 ≥0.5 才能替换。防止 agent 在一个 session 内刷高分项。

### 校准 loop
每个 spotlight 进日志，带空白 `outcome:` 字段。用户慢慢标 `hit` / `miss`。30 条后阈值调整：
- <30% 命中率 → 阈值 +0.5
- >70% 命中率 → 阈值 −0.5

这是防止规则陈旧的 loop。

## 评分细则

### Leverage Type（权 0.4）

基于 Naval Ravikant 的杠杆栈：

| 分 | 类型 | 例子 |
|---|---|---|
| 10 | 无需许可的代码/媒体 | 软件 primitive、长青内容 |
| 7 | 资本 | 不对称的财务下注 |
| 5 | 劳动杠杆 | 招人、授权 |
| 3 | 流程杠杆 | 自己工作的 SOP |
| 1 | 纯劳动 | 自己亲手干 |

### Specific Knowledge（权 0.3）

| 分 | 类型 | 例子 |
|---|---|---|
| 10 | 你的护城河 | 拥有你完整 stack 的人才会知道的东西 |
| 7 | 领域特定 | 适用于你的行业 |
| 5 | 通用 ops | 时间管理、生产力 |
| 3 | 商品信息 | 任意一本商学院书里都有 |
| 1 | 真理 | 「努力会有回报」 |

### First-Principles Surprise（权 0.3）

| 分 | 类型 | 例子 |
|---|---|---|
| 10 | 打破假设 | 「成本比假设低 10×、影响高 10×」 |
| 7 | 实质性偏移 | 有意义地更新模型 |
| 5 | 确认模型 | 给你既信的东西新证据 |
| 3 | 重述已知 | 听过这个 |
| 1 | 真理 | known-known |

## 为什么是这些权重

- **Leverage 0.4** 因为杠杆是创始人/创作者尺度上影响最大的决定项。
- **Specific Knowledge 0.3** 因为锐化边缘的洞见在整个职业生涯里都在复利，通用 ops 洞见回报是平的。
- **Surprise 0.3** 重重推开谄媚但不主导分数。

如果你给 Surprise 加更高（比如 0.5），规则会开始对「为了反对而反对」的内容触发。0.3 够防「你说得对」回路，不奖励边缘。

## 什么时候打破规则

Spotlight Rule 是默认，不是法律。Override case：

- **用户主动要 agent 的意见** — 他们邀请输入了，规则不适用。
- **高风险安全** — 真正的钱 / 健康 / 法律风险无论分数都应该浮出。
- **批量分流模式** — `/sprint-planning` 或 `/pipeline-review` 期间用户预期多候选。

Override 时也要 log 到 `spotlight-log.md` 加 "override" 注 — 保证校准数据干净。

## 这条规则 **不** 做的事

- **不替代人的判断。** Spotlight 是「考虑一下」，不是「做这个」。
- **不抓所有东西。** 一些有价值的项会因为高影响高 effort 而打不到 7.0。OK — 它们走正常 task 浮现，不走 spotlight 浮现。
- **第一天不工作。** 校准 loop 需要 ~30 条来开始调。第一个月用默认 7.0；预期会错过一些。
